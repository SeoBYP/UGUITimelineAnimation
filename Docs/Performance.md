# 성능 측정과 최적화 기록 (2026-10-15)

UI Animation이 Animator·DOTween·LitMotion 없이도 성능상 손해가 없는지(증명 목표 2)를 재고, 그 과정에서 찾은 비용을 줄인 기록입니다.
- 결과 표 전체: [`Benchmarks.md`](Benchmarks.md)
- 측정 프로젝트와 실행 방법: [`Benchmarks/README.md`](../Benchmarks/README.md)

## 1. 결론

IL2CPP 릴리스, 2,000개 기준입니다. 괄호는 같은 값을 스크립트로 직접 넣는 경우(기준)보다 더 든 시간 = 그 방식 자체의 비용입니다.

| | UI Animation | DOTween Pro | LitMotion | Animator | AnimationUI |
|---|---:|---:|---:|---:|---:|
| 맥박 반복 (ms) | 7.69 (+0.38) | 7.71 (+0.40) | **7.66 (+0.34)** | 10.16 (+2.85) | 9.31 (+2.00) |
| 목록 등장 (ms) | 1.70 (+0.04) | 1.59 (−0.06) | **1.53 (−0.13)** | 5.23 (+3.57) | 2.18 (+0.52) |
| 글자 물결 100개 (ms) | **0.61** | 2.11 | 2.05 | 지원 안 함 | 지원 안 함 |
| 매 프레임 GC (기준 대비) | **0** | 맥박 0, 등장 +11KB | **0** | +0.1KB | +16KB |

Burst 일괄 계산(4.5) 적용 후, 한 번 실행한 값입니다. 방식 사이 0.1ms 안쪽 차이는 실행마다 바뀌는 범위입니다(5절).

- **Animator·AnimationUI보다 빠릅니다.** 맥박 2,000개에서 자체 비용이 약 1/5~1/7입니다(+0.38ms 대 +2.0~2.9ms).
- **코드 트윈과 같은 수준입니다.** 맥박 2,000개에서 DOTween Pro(+0.40)·LitMotion(+0.34)과 차이가 0.05ms 안쪽입니다.
- **글자 효과는 가장 빠릅니다.** 텍스트 100개에서 DOTween Pro·LitMotion의 약 1/3입니다.
- **재생 중 GC 할당이 없습니다.** 반복 재생에서 매번 할당하는 DOTween(목록 등장 2,000개 기준 프레임당 11KB)·AnimationUI(코루틴)와 다릅니다.
- **약한 곳: 재생 시작 비용.** 목록 등장에서 2,000개를 한 번에 다시 재생하는 데 2.31ms가 듭니다(LitMotion 1.34ms, DOTween 3.89ms). Burst 일괄 계산이 키를 묶어 두는 일을 더해 조금 늘었습니다(4.5). 한 프레임에 수천 개를 동시에 시작할 때만 드러납니다.

목록 등장에서 기준보다 빠른(음수) 값은 측정 방식 때문입니다. 기준 스크립트는 연출이 끝난 뒤에도 매 프레임 값을 계속 넣고, 라이브러리들은 0.4초 뒤 멈춥니다. 그 구간에서 기준이 일을 더 하므로, 0 근처 값은 "차이 없음"으로 보면 됩니다.

## 2. 측정 방법

- **같은 화면을 다섯 방식으로**: 같은 오브젝트(이미지 N개, 텍스트 N개)에 같은 연출을 방식별로 붙였습니다. 연출은 맥박 반복, 목록 등장(0.5초마다 다시 재생), 글자 물결입니다.
- **기준(직접 대입)**: 애니메이션 시스템 없이 스크립트 하나가 매 프레임 같은 값을 넣습니다. 바뀐 UI를 uGUI가 다시 그리는 비용은 모든 방식에 같이 들어 있어서, 기준과의 차이로 각 방식의 비용을 봅니다.
- **환경**: Windows 64비트 플레이어 1280×720 창 모드, VSync 끔, 프레임 제한 없음. 경우마다 1초 예열 후 4초 동안 매 프레임 기록했습니다. CPU는 AMD Ryzen 7 7800X3D, Unity 6000.6.3f1입니다.
- **시간**: 릴리스 빌드(Mono, IL2CPP)의 프레임 시간입니다.
- **GC**: 개발 빌드로 따로 쟀습니다. 이유는 3.1에 적었습니다. 측정 시작 때 1MB를 할당해 카운터를 확인합니다. 결과 첫 줄에 `probeRecorder: 1048659`가 남아, 1MB가 정확히 잡혔습니다.
- **자동화**: 빌드·실행·표 작성까지 모두 CLI로 합니다. Unity 에디터 화면은 조작하지 않았습니다.

## 3. 측정하면서 생긴 문제

| 문제 | 원인 | 처리 |
|---|---|---|
| 릴리스 빌드에서 GC가 전부 0 | 할당 카운터 `GC Allocated In Frame`이 개발 빌드에서만 동작. `GC.GetTotalAllocatedBytes`는 이 API 프로필에 없음 | 시간은 릴리스, GC는 개발 빌드로 나눠 측정. 할당량은 빌드 종류와 무관 |
| AnimationUI 목록 등장에서 실행이 멈춤 (`NullReferenceException: routine is null`) | AnimationUI 버그. 대기 단계 없는 시퀀스는 첫 프레임에 코루틴이 끝나 `StartCoroutine`이 null을 돌려줌. 다음 `Play()`의 `Stop()`이 `StopCoroutine(null)` 호출 | 측정용 시퀀스 끝에 대기 단계를 붙여 피함. 실행기는 한 경우에서 예외가 나도 다음 경우로 넘어가게 함 |
| 결과 파일이 한 파일에 덮어써짐 | 실행 명령의 따옴표 안에서 `\$out`이 문자 그대로 쓰여 세 측정이 같은 파일(`Results$out.jsonl`)에 기록 | 중간에 멈추고, 경로를 스크립트 파일로 넘기도록 바꿔 다시 측정 |
| DOTween Pro가 다른 프로젝트에 설치됨 | 메인 프로젝트에 Import됨 | 측정 프로젝트로 복사(저장소에는 넣지 않음, `.gitignore`). TMP 모듈 정의(`DOTWEEN_TEXTMESHPRO`)는 설정 스크립트가 켬 |

## 4. 최적화

최적화 전 코드로 먼저 전체를 재 두고(`Benchmarks/Results/history/1-…`), 고친 뒤 같은 조건으로 다시 쟀습니다(`2-…`). 모두 Mono 릴리스입니다. 그때는 DOTween이 아직 없었습니다.

### 4.1 글자 효과: 매 프레임 레이아웃 다시 하지 않기 (`UIAnimTextChars`)

- **전**: 글자 트랙이 있는 텍스트는 매 프레임 `ForceMeshUpdate()`로 글자 배치 전체를 다시 계산하고, 그 위에 글자별 변형을 얹었습니다.
- **후**: 처음 한 번 배치한 정점·색을 저장해 둡니다. 매 프레임에는 저장본을 메시에 복사하고 변형만 적용합니다. 텍스트·크기·색·노출 글자 수처럼 TMP가 다시 배치해야 하는 변경(`havePropertiesChanged`)이 있거나 정점 수가 바뀔 때만 다시 배치합니다.
- **나중에 고친 것 (RPG 샘플 승리 화면)**: 사각형 크기만 바뀌는 경우(배너가 커지며 그 안의 제목도 넓어짐)는 TMP가 `havePropertiesChanged`로 알려 주지 않아, 좁을 때의 줄바꿈이 남았습니다(승리 화면 "VICTO / RY"). 배치할 때의 크기를 기억해 두고 달라지면 다시 배치합니다. 테스트 `글자_효과_중에_상자가_넓어지면_줄바꿈을_다시_한다`.

| 텍스트 수 | 전 | 후 | LitMotion (같은 측정) |
|---:|---:|---:|---:|
| 10 | 0.61 ms | 0.34 ms | 0.63 ms |
| 50 | 1.88 ms | 0.65 ms | 1.96 ms |
| 100 | 3.64 ms | **0.98 ms (3.7배)** | 3.57 ms |

`§13`의 "글자 효과 최적화(텍스트당 약 0.2ms/프레임)" 항목은 이것으로 끝났습니다.

### 4.2 재생 경로: 매 프레임 할 필요 없는 일 빼기 (`UIAnimation`)

| 고친 것 | 전 | 후 |
|---|---|---|
| 상태 길이 | 반복 상태가 매 프레임 `Duration`을 다시 계산(모든 트랙 순회 + 스레드별 정적 변수 접근) | 재생 시작 때 한 번 계산해 저장(`Playback.duration`) |
| 이벤트·사운드·자식 호출 확인 | 하나도 없는 상태도 매 프레임 목록을 돌고 스레드별 깊이 변수를 증감 | 재생 시작 때 있는지 기록(`hasMarkers`), 없으면 바로 돌아감 |
| `.transform` | 대상이 이미 Transform인데 매번 `.transform`(네이티브 호출) | 대상이 Transform이면 그대로 씀 |

맥박 반복의 자체 비용(기준과의 차이)은 다음과 같이 줄었습니다.

| N | 전 | 후 |
|---:|---:|---:|
| 500 | +0.31 ms | +0.15 ms |
| 1,000 | +0.54 ms | +0.33 ms |
| 2,000 | +1.22 ms | **+0.59 ms (약 절반)** |

### 4.3 해 보고 되돌린 것

- **트랙마다 하는 Unity null 검사 빼기**: 파괴된 대상은 쓰기 시점의 예외로 처리하게 바꿔 봤습니다. 2,000개에서 8.694 → 8.675ms로 오차 범위였습니다(`history/3-…`). 코드만 복잡해져서 되돌렸습니다.

### 4.4 남은 비용

에디터에서 2,000개 상태를 직접 돌려 부분별 시간을 쟀습니다. 에디터라 플레이어보다 느리고, 비율만 참고합니다.

| 부분 | 프레임당 |
|---|---:|
| 전체 (`Lap`) | 1.79 ms |
| 값 계산 (`Sample`, 트랙 2개) | 0.64 ms |
| 값 쓰기 (`Write`, Unity 속성 설정) | 0.71 ms |
| null 검사 | 0.08 ms |

- 값 쓰기는 직접 대입과 같은 Unity 속성 설정이라 줄일 수 없습니다.
- LitMotion과의 남은 차이(2,000개에서 0.2ms 안팎)는 대부분 값 계산과 상태마다의 타이머 호출입니다. LitMotion은 Burst로 컴파일된 일괄 계산을 씁니다.
- 이 중 값 계산은 4.5에서 Burst 일괄 계산으로 옮겼습니다. 남은 후보는 재생 시작 때 키 값 해석(`Resolve`) 비용입니다.

### 4.5 Burst 일괄 계산 (`UIAnimBatch`)

LitMotion처럼 재생 중인 모든 트랙의 값을 Burst로 컴파일한 함수 한 번에 계산합니다. `com.unity.burst`가 필수 의존성이 됐습니다.

- **흐름**: 매 프레임 타이머가 콜백을 돌기 전에 `UIAnimBatch.Run`이 Burst 함수 하나를 부릅니다. 재생마다 지금 시간(반복·역재생 포함)을 구하고, 트랙마다 키 구간을 찾아 이징·보간한 값을 배열에 씁니다. 이어서 재생별 콜백은 그 값을 Unity 속성에 쓰고 이벤트를 울리기만 합니다. 이벤트·완료 순서는 그대로입니다.
- **대상**: 키가 모두 이징 프리셋인 트랙입니다. AnimationCurve·Punch·Shake 키, 글자별 트랙, 무작위 글자(scramble) 노출은 전처럼 관리 코드로 계산합니다.
- **같은 값 보장**: 배치는 타이머 콜백과 같은 산술로 시간을 구하고, 콜백이 받은 시간이 배치 시간과 정확히 같을 때만 배치 값을 씁니다. 다르면(테스트가 직접 넘긴 시간, 첫 포즈, 이번 프레임에 시작한 재생) 관리 코드로 계산합니다. 테스트 `UIAnimBatchTests`가 Burst 값과 `UIAnimTrack.Sample` 값이 1e-4 안에서 같은지 확인합니다.
- **재생 시작**: 재생마다 키를 새로 묶으면 시작 비용이 IL2CPP 2,000개에서 2.73 → 3.88ms로 늘었습니다. 재생마다 자리를 계속 쓰고(같은 재생은 같은 자리에 덮어씀), 확인과 복사를 한 번의 루프로 합쳐 줄였습니다.
- **Burst 컴파일 확인**: 플레이어 빌드의 `lib_burst_generated.txt`에 `SeoBYP.TimelineAnimation.UIAnimBatch::Sample`이 들어 있습니다.

측정은 같은 PC에서 전(Burst 없음)·후 빌드를 번갈아 3번씩 돌린 중앙값입니다(`Benchmarks/Results/ab/`, `-benchOnly Baseline,UIAnimation`). 한 번씩 재면 기준(직접 대입)까지 15% 흔들려서 이렇게 바꿨습니다. 프레임 시간 중앙값(p50)에서 기준을 뺀 값입니다.

| 경우 | IL2CPP 전 | IL2CPP 후 | Mono 전 | Mono 후 |
|---|---:|---:|---:|---:|
| 맥박 1,000 자체 비용 | +0.158 ms | +0.129 ms | +0.417 ms | +0.262 ms |
| 맥박 2,000 자체 비용 | +0.326 ms | **+0.274 ms** | +0.798 ms | **+0.502 ms** |
| 목록 등장 2,000 다시 재생(시작) | 2.12 ms | 2.41 ms | 3.01 ms | 3.47 ms |
| 글자 물결 100 | 변화 없음 | | 변화 없음 | |

- 재생 중 비용은 Mono에서 약 37%, IL2CPP에서 약 16% 줄었습니다. IL2CPP는 원래 관리 코드도 C++로 컴파일되므로 Burst로 얻는 몫이 작습니다.
- 재생 시작 비용은 2,000개에서 0.3~0.5ms 늘었습니다. 0.4초 연출이면 프레임마다 아끼는 몫이 몇 프레임 안에 이것을 넘습니다.
- 준비(Setup) 할당이 2,000개 상태에서 약 1.2~1.4MB 늘었습니다. 묶은 키 배열이 두 배씩 커지며 한 번 잡는 용량이고, 재생 중 할당은 여전히 없습니다.
- 글자 물결은 글자별 트랙이라 대상이 아니어서 변화가 없습니다.

## 5. 다시 재려면

1. 빌드:
   ```
   Unity -batchmode -projectPath Benchmarks -executeMethod Bench.BenchBuild.Setup -quit
   Unity -batchmode -projectPath Benchmarks -executeMethod Bench.BenchBuild.BuildMono -quit
   ```
   `BuildIl2cpp`, `BuildMonoDev`도 같은 방식입니다.
2. 실행: `Benchmarks/Builds/<Mono|IL2CPP|MonoDev>/Bench.exe -benchOut Benchmarks/Results/<mono|il2cpp|mono-dev>.jsonl`
3. 표 작성: `python Tools/bench_report.py` → `Docs/Benchmarks.md`
4. 두 빌드 비교(A/B): 빌드 폴더를 `<Mono|IL2CPP>-before`, `-burst`로 복사해 두고 번갈아 `-benchOnly Baseline,UIAnimation`으로 실행합니다. 결과는 `Benchmarks/Results/ab/`.

결과는 한 번 실행한 값이라 경우마다 ±5% 정도 흔들립니다. 예를 들어 맥박 2,000개 UI Animation의 자체 비용은 Mono 측정 두 번에서 +0.59ms와 +0.79ms가 나왔습니다.
